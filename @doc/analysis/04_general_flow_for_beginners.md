# 비전공자를 위한 애플리케이션 흐름 안내

백엔드 서버가 어떻게 동작하는지 쉽게 이해하기 위해 **식당**에 비유하여 설명합니다.
클라이언트(앱이나 웹사이트)는 **손님**이고, 서버(백엔드)는 **식당**이라고 생각해보세요.

## 식당의 구성 요소

1. **경비원 (Filter Layer / 보안 필터)**
   - 역할: 손님이 식당에 들어오기 전 입장 자격이 있는지 확인합니다.
   - 실제 적용: 사용자가 로그인했는지 인증서(JWT 토큰)를 확인합니다. 인증서가 없거나 위조되었다면 쫓아냅니다.

2. **웨이터 (Controller Layer / 컨트롤러)**
   - 역할: 손님의 주문을 받고, 주문서가 제대로 작성되었는지 확인합니다. 요리를 직접 하지 않습니다.
   - 실제 적용: 클라이언트로부터 인터넷 요청(HTTP)을 받아들입니다. 빈칸은 없는지, 글자 수 규칙은 맞는지(`@Valid`) 검사한 뒤 요리사에게 넘깁니다.

3. **주방장 (Service Layer / 서비스)**
   - 역할: 웨이터가 가져온 주문서를 보고 본격적인 요리를 시작합니다. 재료의 상태를 확인하고, 부족하면 요리를 멈춥니다(예외 발생).
   - 실제 적용: 핵심 비즈니스 로직이 들어있습니다. 이메일 중복 체크를 하거나 비밀번호를 암호화합니다. 작업 중 문제가 생기면 작업을 이전 상태로 되돌립니다(트랜잭션).

4. **창고 관리인과 냉장고 (Mapper & Database / 매퍼와 DB)**
   - 역할: 주방장이 필요한 재료를 요청하면 냉장고에서 꺼내오거나, 요리가 완성되면 창고 장부에 기록합니다.
   - 실제 적용: 데이터베이스(MySQL)에 안전하게 데이터를 저장하고(INSERT), 필요한 정보를 꺼내옵니다(SELECT).

## 실제 흐름 예시: 회원가입

1. **손님의 주문 (요청)**: 스마트폰 앱에서 이메일과 비밀번호를 입력하고 '회원가입' 버튼을 누릅니다.
2. **웨이터의 확인 (Controller)**: 웨이터가 폼을 확인합니다. "음, 비밀번호가 너무 짧네요."라고 하면 바로 다시 쓰라고 돌려보냅니다. 정상적이라면 주방장에게 넘깁니다.
3. **주방장의 요리 (Service)**: 주방장은 창고 관리인에게 "이 이메일 쓰는 사람 이미 있어?" 라고 묻습니다. 없다고 하면, 비밀번호를 아무도 못 알아보게 암호화하여 회원 정보를 가공합니다.
4. **창고 저장 (Mapper & DB)**: 창고 관리인은 주방장이 넘겨준 회원 정보를 장부(DB)에 꼼꼼히 기록합니다.
5. **서빙 (응답 반환)**: 기록이 완료되면 주방장은 회원 고유 번호 등 최소한의 정보만 웨이터에게 넘깁니다(비밀번호 같은 민감한 정보는 숨깁니다). 웨이터는 정해진 규격의 쟁반(`GlobalRes`)에 담아 손님에게 "가입 완료되었습니다!" 라고 서빙합니다.

이처럼 역할을 명확히 쪼개두면(레이어드 아키텍처), 문제가 발생했을 때 누구의 잘못인지 파악하기 쉽고 유지보수가 매우 편리해집니다.
